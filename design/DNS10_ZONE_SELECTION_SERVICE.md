# DNS10 — selected-zone administration candidate

Status: source-only administrative service contract. There is no live endpoint, UI, repository adapter, scheduled record collection or migration deployment in this increment. The existing DNS9 zone-list schedule continues independently.

An administrator chooses source-scoped zones from the current successfully discovered zone list. A first selection creates a new immutable dataset identity with `selected=true` and `collection_enabled=false`; saving a selection **must not** start record collection. Enabling record collection is a separate explicit per-dataset action. Only eligible primary and secondary authoritative zones in the default instance/default scope may be enabled; stub, cache, forwarding and unknown types are rejected. The same zone name on different sources remains independent. Unsupported non-ASCII or escaped binary labels are rejected rather than silently rewritten; IDNA support is a separate future requirement.

The caller supplies the exact discovery job ID last presented to the administrator. Under the shared DNS configuration guard, the repository must return the latest complete successful discovery result bound to the current source revision, binding epoch, current collector and assignment revision. A missing, stale, superseded, malformed or differently scoped result cannot authorize selection or enablement. At most 64 datasets may be selected per source. Dataset IDs, canonical source/zone/scope and retained observations are never silently reassigned. Selection and per-zone collection switches use optimistic dataset revisions; a real change increments the revision, so in-flight work becomes stale.

For selection or enabling, the discovery result must be no more than `max(900 seconds, 3 × configured source interval)` old and at most 300 seconds ahead of the server clock. Unsupported names elsewhere in a valid discovery list may be skipped, but a malformed descriptor or ambiguous duplicate of the requested zone fails closed. This is an administrative freshness check, not proof that a zone cannot change immediately afterward; the future worker and publication checks still apply.

Deselection disables per-zone record collection in the same transaction but retains prior observations and sequence state. Explicit disabling must remain possible without a current discovery result or reachable collector. Re-selecting a dataset must not automatically re-enable collection. Enabling requires a selected dataset, enabled source, current collector assignment and current eligible discovery; it does not itself create a job. A future scheduler must separately require both selected and collection-enabled flags and current revisions.

This service's actor ID is an audit identity, **not** authentication. A future phpIPAM route must enforce an authenticated administrator session, CSRF, applicable recent reauthentication and trusted HTTPS before constructing or invoking it. Audit writes and configuration updates must share the same transaction. Database migration and runtime rollout need explicit approval and must not disrupt the active DNS9 zone-list scheduler. DNS writes and native IPAM mutations remain prohibited.
